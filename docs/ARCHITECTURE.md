# 架构与实际工作流

## 一次文本请求

1. Agent 通过 MCP 工具或 CLI 提交问题。
2. 本地 Bridge 验证安装 token，选择目标标签，将请求加入该标签的串行队列。
3. 扩展通过本地 WebSocket 接收任务，在 ChatGPT 页面输入并发送。
4. 页面脚本观察回答，等待完整输出，返回正文和真实会话 ID。
5. Bridge 保存任务状态及本地消息记录，把 JSON 结果交还 Agent。

本地程序不运行大模型，也不调用官方付费 API。它连接的是浏览器中已登录的 ChatGPT 会话。

## “网页大脑 + 本地执行者”

网页 ChatGPT 负责规划与评审。本地 Agent 负责读写文件、运行工具和测试。执行者把必要的问题或执行结果发给网页，取得下一步计划，执行后再回报。Skill 规定这套协作方式；不开启多轮规划时，同一服务也能直接回答一个普通问题。

## 图片请求

Agent 提供本地图片路径和问题。Bridge 校验文件，扩展将图片上传到指定 ChatGPT 标签页，确认附件就绪后发送问题并读取回答。图片通过文件上传，不依赖系统剪贴板。`request_id` 标识一次任务：连接中断或等待超时后先查询原 ID，避免重复上传和重复发问。

## 接着历史聊天

`open_chatgpt_conversation(url)` 验证地址，优先复用已打开的同地址标签，否则打开该旧会话。页面与目标连接就绪、地址和会话身份匹配后才返回 `target_id`。后续问题和图片都传该目标。多个标签使用不同目标；每个目标内部按顺序处理，避免对话串线。

网页中的历史由 ChatGPT 账户保存；本地 SQLite 保存桥接抓取到的消息、任务状态和恢复信息。本地数据库不是网页全部历史的完整备份。

## 为什么看起来组件很多

只有浏览器网页、扩展和 Bridge 是核心运行链路。EXE 是 Bridge 的托盘管理器；MCP 和 CLI 是供不同 Agent 使用的两个入口；Skill 是说明书。通常双击快捷方式后，让 Agent 使用 MCP 即可，不需要同时操作命令行。

## 数据与清理

- `src/`、`extension/`、`launcher/`：核心源码。
- `runtime/venv/`：运行依赖，保留。
- `runtime/edge_profile/`：旧测试用浏览器配置；清理只处理可重建缓存和组件模型，保留账户状态。
- `data/`、`config/config.json`、`extension/config.js`：本机任务数据与安装配置，不发布。
- `tmp/`、`__pycache__/`、旧 `build/*.zip`：可重建产物，由清理脚本预览后清理。
- `build/GPT Web MCP.exe`：托盘入口，需要项目目录和 Python 环境；不是独立打包了 Python 的程序。

运行时仅连接回环 Bridge；与 ChatGPT 的网络交互由原浏览器会话完成。公开仓库不含本机 token、浏览器资料和聊天数据库。
